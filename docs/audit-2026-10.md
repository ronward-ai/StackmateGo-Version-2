# StackMate Go — audit, October 2026

The second full sweep. It covers the whole app, weighted to the **117 commits and ~25,000 changed
lines** since `docs/audit-2026-09.md`, which is now fully cleared. That covers device control and the
one write door, the rebuy offer and failsafe, final tables and table breaks, results columns and
exports, Recent Players, setup sync, per-account storage, the read-only console and the landing page.

**Baseline at the time of writing (`c16c2db`):**
- `tsc` is clean.
- **1,157 unit tests pass (72 files).**
- **64 Firestore rules tests pass** against the emulator.
- The build is clean.

Nothing here is currently *failing*; it is all latent, like last time. The test run is noisier than it
needs to be. It logs seven React `act()` warnings, and a Radix *"Missing `Description`"* warning for at
least one `DialogContent`. The rest of the stderr is tests deliberately exercising failure paths.

**Status — updated as findings are cleared.** Fixed so far: **C1, M8, H3, H4, H1, M1, H2, M2, M4, H6, M3**, the anonymous `userSettings` writer and the rules-coverage gap. **The rules changes need deploying by hand.** Finding IDs are local to
this file; fix commits cite them as **"Oct H3"** etc.

**How it was done.** Six reviewers each took one area:
- live-game integrity;
- game-flow rules;
- league and money;
- security and rules;
- accounts and storage;
- drift and coverage.

Every finding kept here was then checked against the cited lines.

**Reproduced** means it was demonstrated rather than reasoned about, by one of three means:
- a scratch test running the real modules (the lib functions, or the real `useTournament` with
  Firebase mocked);
- a throwaway rules test against the emulator;
- wouter's real router.

None of that scaffolding is in the repo. Where a rules finding is listed, the test to add is given in
full, because it is the regression test the fix needs.

Findings are ranked by severity. The last sections record what is clean, so this ground is not covered
a third time.

## Critical

### C1 — A live game's local mirror is restored as a NEW local game, which the auto-save turns into a duplicate document

**Reproduced** (the restore, with the real `useTournament`). The auto-save hop is confirmed by reading.

**Where:**
- `hooks/useTournament.ts:515`: the mirror keys on `state.details?.localGameId ?? getOrCreateLocalGameId()`.
- On `/tournament/{id}/director`, `details` never has a `localGameId`:
  - `lib/localGameId.ts:55` returns `{type:'database', id}`;
  - the `getDoc` transform does not add one.
- So game G's roster is mirrored under **this device's own local id L**, and one is minted and stored if
  there is none. That is the very thing the thunk in `initialDetails` exists to prevent.
- `useTournament.ts:303` then restores `loadLocalProgress(getOrCreateLocalGameId())` on `/`.
- `lib/localProgress.ts:70` never checks `dbTournamentId`.

**What happens:** any device that resumed G rather than creating it has L ≠ G. That is every handover
and every second device.
1. The device mounts `/` while signed in: a home-screen bookmark, Back, the participant view's home link,
   or the Go home banner.
2. It comes up with G's full roster, bust-outs and level as a local league game.
3. The auto-save (`PokerTimer.tsx:491-545`) sees `live.id !== localGameId` and **creates a second
   document L holding G's roster**. It pins L (`:539`).
4. The next launch opens L. `findCurrentLiveTournament` can rank it above G, so other devices resume the
   copy too.
5. In a league game the recorder files bust-outs under `gameId = L`. `recordResultByName` dedupes on
   (player, tournament), so the league gets **a second result per player and one extra game played**.

This breaks CLAUDE.md's own rule: *"Automatic restore is unchanged — only when
`details.type !== 'database'`."*

**Fix:**
- Key the mirror on `details.localGameId ?? details.id`, because the document id IS the local id.
- In the restore at `:303`, refuse any mirror carrying `dbTournamentId`. That shape belongs only to
  `recoverableProgress`.

**C1 and M8 are one root cause:** two derivations of "this game's id".

## High

### H1 — Anyone can squat a director's deterministic settings id, crashing their console and every participant's phone

**Reproduced** (emulator, plus a hook test).

**Where:**
- `firestore.rules:270`: `allow create: if isRegistered() && isDocUser()`. Nothing binds `{settingId}` to
  the writer.
- `lib/leagueSettingsId.ts:23`: the id is `${ownerId}_${leagueId || 'standalone'}`. Both parts are public
  on every tournament document.
- `hooks/useLeagueSettings.ts:369` adopts the document's `settings` with no `userId` check and no shape
  check.

**What happens:**
1. Any free account writes `leagueSettings/{A}_standalone`, a slot the app never creates (the dialog
   returns early with no league), or `{A}_{L}` before the director next saves.
2. The director is then **locked out**: their save is an update to a document whose `userId` is not
   theirs, and it is denied with a toast on every change.
3. A document with no `settings` field leaves `settings === undefined`. The next render throws on
   `settings.pointsSystem` (`:541`). That hook runs on the director's own Players tab
   (`PlayerSection.tsx:85`, keyed on `details.ownerId`) and in the participant view
   (`RealTimeLeagueTable.tsx:67`), under the single app-level error boundary.
   - **Every console and every phone for that director's games shows the error screen**, on every
     reload.
   - Only the Firebase console can clear it.
4. A document with well-formed attacker settings is instead **adopted silently**, and standings are
   scored by the attacker's scheme.

**Same shape, lower impact:**
- **`completedTournaments/{ownerId}_{localGameId}`** (`firestore.rules:281`). **Reproduced:** a stranger
  pre-creates it and the director's history write is denied, losing that game's history with a toast
  that keeps retrying.
- **`seasons/{leagueId}-season-1`** (`useSeasons.ts:194`). Tiny window, Low.

**Fix:**
- In the rules, bind the deterministic id to the writer on create:
  `settingId.matches(request.auth.uid + '_.+') || !settingId.matches('.*_.*')`. Auto-ids carry no
  underscore. Do the same for `completedTournaments` (`recordId.matches(request.auth.uid + '_.+')`).
- In the client:
  - ignore a remote default whose `userId !== targetOwnerId`;
  - run the `loadFromStorage` shape check before `setSettings`;
  - never `writeScoped` from a participant read.
- **Rules are deployed by hand.**

```ts
it("stops a stranger squatting a director's deterministic ids", async () => {
  for (const id of [`${DIRECTOR}_${LEAGUE}`, `${DIRECTOR}_standalone`])
    await assertFails(setDoc(doc(stranger(), 'leagueSettings', id), { userId: OTHER_DIRECTOR }));
  await assertSucceeds(setDoc(doc(director(), 'leagueSettings', `${DIRECTOR}_${LEAGUE}`),
    { userId: DIRECTOR, leagueId: LEAGUE, isDefault: true, settings: {} }));
  await assertFails(setDoc(doc(stranger(), 'completedTournaments', `${DIRECTOR}_g1`), { ownerId: OTHER_DIRECTOR }));
});
```

### H2 — The signed-out storage bucket is adopted by EVERY later account, and pushed into their cloud copy

**Reproduced** (the real `scopedStorage`, `localProgress`, `recentPlayers` and `setupSync`). M11 from
September is not fully closed.

**Where:**
- `lib/scopedStorage.ts:240-264`: `claimStorageFor` copies `::local` into the account's bucket and
  leaves it in place. Unlike legacy keys (`LEGACY_CLAIM_KEY`), nothing records that it was adopted.
- `useAuth.ts:165-172`: logout clears only the pin and `lastSignedInUid`.

**What happens:**
1. Director A starts signed out, which is the ordinary first use, and builds a structure, branding and
   a roster.
2. A signs in, and everything is copied.
3. A logs out. The signed-out console on `/?home=1` shows A's roster again.
4. Account B signs in for the first time on that browser. B inherits A's structure, event name, logo,
   roster and recent names.
5. Then:
   - `useDirectorSetupSync` finds no remote setup and **pushes A's setup into `userSettings/B`**;
   - `useRecentPlayers` finds no cloud list and **pushes A's player names into B's account**, after
     which they follow B to every device.

Plausibly, B's auto-save also mints `createTournamentDocument(docId = game_A)`, gets a 409 and adopts A's
live game.

**Fix:** keep copy-not-move, but retire the source once it is adopted. Move it to `::local@<uid>`, or
stamp an "adopted by" marker the way `LEGACY_CLAIM_KEY` does. A test must cover "started signed out,
then a second account".

### H3 — Starting the next game from the director route silently drops everything it was told to set

**Reproduced** (wouter's real `Switch`).

**Where:** `hooks/useNewGame.tsx:52-60` runs `resetTournament(…)`, then `setLocation('/?home=1')`, then
`after()`. From `/tournament/:id/director` that navigation swaps the whole route tree **in the same
batch**, so neither the reset state nor `after()`'s `setState`s ever commit.
- The new mount rebuilds from storage.
- Only the synchronous `writeScoped` of the new local id survives.

**What breaks:** most signed-in directors are on this route, because every refresh or resume lands
there.
- **Next Game with a chosen season** keeps the old season. After "Start next season" the old season is
  the ended one, so results are filed there and "Game 13 of 12" returns. That regresses the
  ended-season fix.
- **The slider's finished league → Standalone** comes up in League mode, so the casual night records
  into the league.
- **Full reset** does nothing.

**Fix:** persist the new game's settings and details synchronously before navigating (a scoped
"pending new game" blob read by `initialState`), or do a full `window.location` load after writing
everything.

### H4 — Moving between games on the director route reuses the console, and writes game A's state onto game B

**Reproduced** (wouter keeps the same instance across `/tournament/A/director` → `/tournament/B/director`).
The writes are confirmed by reading.

**Trigger:** `useOpenLiveGame` (the other-live-game banner, and *Open that game*).

**What happens:** `consoleTournamentId()` makes the URL id definitive, so `activeTournamentId` becomes
B at once. But:
- `hasLoadedRemoteState` is still A's latch. It is reset only in the parent's listener effect, which runs
  after the child's sync effects.
- The control fact is A's, labelled as B's.
- `dbTournamentId` is still A. The reset effect returns early on a URL id.

So:
- **(a)** The clock sync writes A's level, `targetEndTime`, blinds and notes onto B. The door allows it,
  because A's holder was "mine".
- **(b)** B's `getDoc` copy is written back to B before its listener has read it, which can revert a
  bust-out the other device made in that window.
- **(c)** Go Live on B **publishes A** (`QRCodeSection.tsx:54` prefers the held id), then repoints the
  listener to A while the syncs write to B.
- **(d)** `pendingRoster`, `processedEliminationsRef` and `useRebuyOffer`'s `seenRef` all carry A's
  memory.

**Fix:** `<PokerTimer key={tournamentId} …>` in `TournamentDirector.tsx`. A fresh mount per game is the
clean slate every guard in that file assumes.

### H5 — Switching league in Manage League mid-game sends the rest of the night into the other league

Confirmed by reading.

**Where:**
- The scope bar's league picker (`LeagueScopeBar.tsx:55`) and **New** (`useLeague.ts:204`) switch the
  league with no gate.
- Every `useLeague` instance follows `leagueSwitched`, including the console's.
- `PokerTimer.tsx:302-338` then falls back to the new league's current season and overwrites
  `settings.seasonId`.

**What happens:** a director looks at another league's seasons during a break. Every later bust-out is
recorded into **that** league, scored with its points scheme, against its season.
- `settings.leagueId` still names the original league, so phones show its standings without tonight's
  later results.
- The console's Points column scores with the original scheme.
- Switching back moves nothing back.

This is the transfer-code failure CLAUDE.md records, by a third door.

**Fix:** the recorder and remover should write to the league stored on the game (`settings.leagueId`),
never to the selected one. Also gate the scope bar while a league game has positions, which is the same
condition as `modeLockReason`.

### H6 — Result claims live in one tab's memory, so after a reload or takeover a corrected result can never be written

Confirmed by reading.

**Where:**
- `PokerTimer.tsx:346`: `processedEliminationsRef` is in-memory and never seeded from the cloud.
- The removal (step 1, `:1046`) and the renumbering correction (step 2, `:1072`) act only on players this
  tab claimed.
- `useLeague.ts:511-516` dedupes on (player, tournament) **whatever the stored position**.

**What happens:**
1. Dave busts 12th and is recorded.
2. The iPad reloads; Safari evicts tabs.
3. Dave re-enters. Re-entry is the late action, and its period defaults to unlimited.
4. Step 1 skips him, because this tab holds no claim, so the 12th stays.
5. He busts 5th. The dedupe finds the 12th and skips.
6. **12th, permanently.** Every finisher renumbered by that re-entry keeps a stale place as well.

The same happens after Take control.

**Fix:** derive the claims from `cloudResults` for this `gameId`, or make steps 1 and 2 consult the
cloud results directly.

### H7 — Finishing positions collide after a late entry or an out-of-order undo, and can produce two winners

**Reproduced.**

**Where:**
- `useTournament.ts:1032`: `addPlayer` renumbers nobody.
- `:1054`: `removePlayer` leaves a gap.
- `:2214`: `undoBustOut` restores one player and never calls `positionsAfterReEntry`.
- `lib/eliminationOrder.ts:157` gives the next place as `players.length − alreadyPositioned`.

**What happens:**
- **Late entry**, which CLAUDE.md supports explicitly: nine players, three busted (9th, 8th, 7th), one
  added. The next bust-out is also **7th**, and nobody is ever 10th.
- **Undo, mid-game:** undo 9th of 9, 8, 7, and the next bust-out is 7th.
- **Undo, finished game:** the director follows *"undo the last bust-out"* and taps the top row of the
  Undo dialog (`TablesSection.tsx:855`), which lists the first player out first.
  - That player is active again.
  - With one active player the champion stays at 1st.
  - Busting them again awards **1st**.
  - **Two winners are recorded to the league.**

**Fix:**
- Lib functions, with tests, for "shift finishers on add / on remove / on undo", called inside the
  updaters.
- On undo of a finished game, re-activate the winner.
- Sort the Undo dialog with the most recent first.
- The dead no-id branch at `:2203` still picks the HIGHEST position, which is the inverted "most
  recently busted"; delete it.

## Medium

### M1 — A check-in can bloat the live document to 1 MiB, or fill `claims` so no-one else can check in

**Reproduced** (emulator).

`firestore.rules:235-238` constrains only `hasOnly(['claims'])`, `claims is map` and the key count.
- An anonymous visitor (the app mints one for everyone) can write `{'claims.p1': 'x'.repeat(200_000)}`,
  or nested maps. Once the document nears 1 MiB, **every director write that grows it fails**
  mid-tournament, and every phone downloads the bloat on every write.
- A whole-map write of junk keys reaches the count, and **every genuine check-in is then refused**.
  Removing players does the same without an attacker, because claims are never pruned.

**Fix:** have the write name its key (a companion `lastClaim` field), require
`claims.diff(resource.data.get('claims',{})).affectedKeys().hasOnly([lastClaim])`, and bound the value
to a string of at most 64 characters. Or move claims into one fully constrained document per seat.

```ts
await assertFails(updateDoc(doc(anonAuth(),'activeTournaments',TOURNAMENT), {'claims.p1': 'x'.repeat(100_000)}));
await assertFails(updateDoc(doc(anonAuth(),'activeTournaments',TOURNAMENT), {'claims.p1': {a:{b:1}}}));
await assertFails(updateDoc(doc(anonAuth(),'activeTournaments',TOURNAMENT), {claims: {junk1:'d', junk2:'d'}}));
```

### M2 — Reset and Delete on one device are undone by any other device holding Recent Players

**Reproduced** (the decision logic).

`useAccountReset.ts:88,168` clears the field with `deleteField()`, and `resolveRecent` reads an absent
field as "no cloud list, push mine" (`recentPlayers.ts:103`). A tablet that ever saw a cloud list re-pushes
its cached names the moment the field disappears. **Delete's "these are real people's names" promise does
not hold.**

**Fix:** write `recentPlayers: []`. The module's own rule, *"an EMPTY cloud list is still a list"*, then
makes every device adopt the empty list.

### M3 — The removal of a league result swallows every error, so "release the claim after the work" never retries

Confirmed by reading.

**Where:**
- `useLeague.ts:597-599` logs and returns.
- So `PokerTimer.tsx:1054-1066` (keep the claim, retry, toast) is unreachable.
- Step 2 (`:1077`) deletes the claim **before** its await and marks the player corrected even when the
  removal failed.

**What happens:**
- On a rebuy, the stale result stays and the re-bust is deduped away silently.
- On a re-entry renumbering, step 3 records with `allowReplace`, giving **two results for one game**.
  Points, games played and Invested all count twice.

September's M10 fix is inert here.

**Fix:** rethrow, and release only after a successful removal.

### M4 — An account change without a page load writes one account's game and setup into another's

Confirmed by reading; Plausible in practice.

`useTournament.ts:258-262` promises *"if auth then resolves to somebody else, the effect below re-reads"*.
**No such effect exists, or ever did.** The mirror writes to whatever `storageUid` now resolves to on every
tick.
- Sign out in a second tab, and the first tab's running clock writes A's live roster into `::local` every
  second, which feeds H2.
- Sign in as B on that tab's *"Sign in to run this game"* screen, and B's setup sync pushes A's settings
  and structure into `userSettings/B`.

**Fix:**
- Re-key on a uid change: reload from the new bucket, or treat it as a logout and force a page load.
- Do not run the mirror or setup writers while `user` is null for a database game.
- Correct the comment.

### M5 — The money in a row disagrees with the money recorded, in three ways

1. **The console's Invested, Profit and Points ignore the rebuy and add-on price** (`resultRows.ts:274`,
   `:281`), while the recorder passes `rebuyAmount`. **Reproduced:** with buy-in 20, a rebuy at 10 and
   "Rebuys cost you", the console shows Invested £40 and **250** points, but **288** points are recorded.
   This reaches the screen, the PNG, the CSV and the phone. Every test fixture uses
   `rebuyAmount === buyIn`, which is why it hid.
2. **A re-entry's buy-in is never charged.** `investedIn` (`resultStats.ts:53`) ignores `reEntries`, and
   its test justifies that with *"a re-entry is recorded as its own result"*, which is false.
   **Reproduced:** `investedIn({buyIn:20, reEntries:2}) === 20`. A player who re-entered twice shows +£40
   profit when they broke even.
3. **A free game is recorded as a £10 game.**
   - On write: `PokerTimer.tsx:1129` and `useLeague.ts:556` (`|| 10`), plus `tournamentDocument.ts:104`.
   - On read: `buyInOf` (`resultStats.ts:43`).
   - A freeroll league shows −£10 and −100% ROI for every player every week. This is September's M5 class,
     arriving at the recorder.
   - **Fix:** `??` on write. Fall back to 10 only for an *absent* field, so old leagues do not move.

### M6 — Bounty money is wrong for progressive bounties, and paid on players who carry none

**Reproduced** (the display); the rest is confirmed by reading.

- **`useTournament.ts:1152-1156`** adds `knockouts × bountyAmount` to `prizeMoney` for every bounty type.
  - In PKO the hunter receives half the victim's current bounty. A PKO player out of the money with one
    KO (worth £5) shows a **phantom Prize £5, Won £10**, and the league's Cash records £10.
  - The PKO winner's `prizeMoney` (`:1218`) omits their accumulated `bountyWinnings`, so league Cash is
    short while the Bounties breakdown is larger than Cash's bounty share. That breaks CLAUDE.md's
    *"a breakdown, never an addend"*.
- **`currentBounty || bountyAmount`** (`:1178`, `:1220`, and `resultStats.ts:113`). A rebuy taken without
  a fresh bounty (the default) stores `currentBounty: 0`, and `0 ||` turns that into a full bounty.
  - Standard bounties pay `bountyAmount` per KO regardless, so knocking out a player who never bought a
    bounty **pays out money that was never collected**.
- **Undo bust-out** (`:2226`) decrements the hunter's knockouts but leaves the transferred half in their
  `bountyWinnings` and `currentBounty`.

**Fix:**
- In PKO, fold `bountyWinnings` into `prizeMoney` for busted players and the winner.
- Pay per the victim's `currentBounty`, using `??`.
- Record the amount taken at bust time, so undo can reverse it.

### M7 — A re-entry renumbers a paid finisher out of the money, and they keep the money

**Reproduced.**

`positionsAfterReEntry` shifts `position` only, never `prizeMoney`. The `resultRows.ts:258` fallback then
shows the stored figure, and step 2 re-records it. With three places paid, the 3rd-place money ends up
**paid twice** on screen and in the league. Reachable because the re-entry period defaults to unlimited.

**Fix:** recompute `prizeMoney` for shifted finishers in `processReEntry` and `processRebuy`.

### M8 — The game number is one too high on any console that loaded the game from Firestore

**Reproduced.**

`gameNumberFor(…, details.localGameId)` is called at `PokerTimer.tsx:307`, `TournamentInfoCard.tsx:113`
and `LeagueSection.tsx:77`. On the director route that id is undefined, while the recorder files results
under `localGameId ?? id`. After the first bust-out the header reads **"Game 5 of 12"** for game 4, and
`settings.gameNumber = 5` is written to every phone and the PNG subtitle.

**Fix:** pass the recorder's `gameId` at all three sites (with C1).

### M9 — A season with no game count advertises "Game n of 12"

`|| 12` appears at:
- `PokerTimer.tsx:312`;
- `TournamentInfoCard.tsx:117`;
- `ParticipantTournamentInfoCard.tsx:30`;
- `NextGameControl.tsx:115,136,141`;
- `useSeasons.ts:183`.

`NextGameControl.tsx:115` also **writes** `numberOfGames: 12` into settings. `gameProgressLabel` already
handles "no count"; the callers inject 12 first. So the toggle row and every phone say "Game 4 of 12", and
game 13 says "Game 12 of 12", while the League panel says "Game 13". This contradicts *"a season with
neither simply never advertises itself as finished"*.

**Fix:** pass `numberOfGames` through untouched, and write nothing.

### M10 — Entry windows count breaks as levels

**Reproduced.**

`lib/entryLimits.ts:80` compares the raw level index, and breaks are entries in `levels`. The clock and the
Add Break picker number levels *excluding* breaks. With one break before level 5 and a period of 5:
- rebuys, re-entries and late entry close during the on-screen **Level 5**;
- add-ons open a level early;
- the late-entry dialog says "level 6" while the clock says 5.

**Fix:** one helper in `entryLimits` that converts the index to the blind-level number, the same numbering
as `announcements.ts`'s `blindLevelNumber`.

### M11 — A level change restarts the clock from "now", so time spent asleep or backgrounded is lost

Confirmed by reading. Both the live-game and game-flow reviewers found it independently.

`useTournament.ts:~815-821` sets `targetEndTime: Date.now() + duration` on the tick that notices the end,
and advances one level per tick. An iPad director switches apps (iOS suspends JS) and comes back 5 minutes
after the level ended. The next level starts at its full 15:00, **the schedule slips 5 minutes**, two
elapsed levels collapse into one, and phones showed 00:00 meanwhile.

**Fix:** chain from `prev.targetEndTime + duration`, and loop over elapsed levels. That is CLAUDE.md's own
*"a running clock is an end time"*.

### M12 — Undoing the final bust-out leaves the game `completed`, with History holding the wrong winner

Confirmed by reading.

The completion effect (`PokerTimer.tsx:370-400`) writes `status: 'completed'` and releases control.
Nothing ever clears `status`, and `savedHistoryRef` blocks a re-save. After the documented correction
(Undo bust-out):
- resume and handover skip the game;
- control stays released;
- the corrected ending never reaches `completedTournaments`.

**Fix:** when `!gameIsOver` on a game whose status is `completed`, clear the status through the door and
reset `savedHistoryRef`.

### M13 — The shared "rebuy answered" set records questions nobody answered, and cannot tell a second bust-out from the first

Confirmed by reading (both reviewers); the key collision is **Reproduced**.

- **Seeded keys are synced as answers.** `useRebuyOffer.ts:121` puts every bust-out present at first load
  into `answered`, which `PokerTimer.tsx:~880-895` writes to `rebuysAnswered`. This is exactly the
  dead-other-device case the failsafe exists for, and CLAUDE.md promises it works:
  - the laptop dies holding the question;
  - the phone opened afresh marks it answered for every device;
  - it gets no failsafe Rebuy.
  - Separately, `seenRef` is never reset per game, so game 1's keys are written into game 2.
- **The key `id:rebuys` ignores re-entries and undo** (`lib/rebuyOffer.ts:51`). Amy busts and the
  director answers "No". She re-enters (her rebuy count is still 0), or her bust-out is undone. When she
  busts again, `amy:0` is already answered, so **a rebuy the rules allow is never asked about.**

**Fix:**
- Keep the seeded set apart from the answered set, and sync only real answers.
- Reset per game id.
- Add the re-entry count and a bust counter to the key.

### M14 — A read-only console never sees a rebuy, re-entry, undo or remove made on the driving device

**Reproduced.**

The merge is local-biased (`lib/snapshotMerge.ts:92,107,120`):
- a busted player stays busted;
- counts take `Math.max`;
- missing players are appended back.

`keepLocal` and `adopt` are both false while read-only, so the second screen shows the rebought player
still out, the undone KO still counted and the removed player still present, **all night**. The takeover's
`adopt` heals it, but the watcher view is wrong until then.

**Fix:** when `!mayDrive(nextControl)`, take the incoming roster as-is.

### M15 — A returning player can be seated on a table that no longer exists, or in an occupied chair

**Reproduced** (lib functions).

- `lib/tableBreak.ts:235-237` renumbers `tableAssignment`, but not busted players' `seatInfo`.
- `seatToReclaim` (`lib/seating.ts:67-83`) never checks the configuration.
- After a break of the middle table, plus a reload (which clears `preConsolidation`), a failsafe rebuy or
